# Incident Command AI

A real-time, multi-user incident operations platform. Live workspaces start empty and use operator records, monitored health endpoints, authenticated telemetry, and connected runtime APIs. An opt-in browser lab creates clearly marked test observations, separate from live metrics.

## Local installation

Use Node.js **22.12+ or 24+**, npm and Git. Docker and kubectl are not required to run the application or browser test labs. A reachable PostgreSQL database is required; AI analysis also needs a valid OpenRouter key and internet access.

### 1. Get the project

For a new checkout:

```bash
git clone https://github.com/PraneethPW/INCIDENTCOMMAND.git
cd INCIDENTCOMMAND
```

If you already have the repository, use the [update steps](#updating-an-existing-local-installation) below. Run all following commands from the repository root.

### 2. Install the locked dependencies

```bash
npm run install:all
```

This runs `npm ci` in the root, backend and frontend, using the committed lockfiles. Install dependencies **before** database setup; this installs the backend's `tsx` executable and prevents `tsx: command not found`.

### 3. Create the two app environment files

```bash
npm run setup:local
```

This creates `backend/.env` and `frontend/.env` when missing and generates a secure local session secret. Existing files and configured secrets are preserved. No root `.env` or `.env.example` is needed. The two `.env.example` files inside the app folders remain safe, tracked templates.

Edit **backend/.env**:

```env
DATABASE_URL=your_complete_postgresql_connection_string
DATABASE_LISTEN_URL=
# Keep the SESSION_SECRET generated by setup; do not replace it.
OPENROUTER_API_KEY=your_openrouter_key
OPENROUTER_MODEL=openrouter/free
OPENROUTER_FALLBACK_MODELS=
PORT=8787
FRONTEND_URL=http://localhost:5173
NODE_ENV=development
```

Keep the actual generated `SESSION_SECRET`. The database and session secret are required. AI is optional until you select **Analyze evidence**; a missing or invalid key cannot produce a live analysis.

For Supabase, copy the complete **Connect → Session pooler** PostgreSQL URL on **port 5432**, including your real database password. The project HTTPS URL is not a database connection string. You can leave `DATABASE_LISTEN_URL` blank when `DATABASE_URL` is already session-capable. See [database connection details](docs/SUPABASE-MIGRATION.md) for TLS and pooling.

Edit **frontend/.env** to contain:

```env
VITE_API_URL=
```

Leave it **blank** for local full-stack use. The browser calls `/api` on localhost:5173, and Vite forwards requests to the backend on localhost:8787. A Railway or Vercel URL here would point the local UI at the deployed application instead. Secrets belong only in `backend/.env`. Restart the servers after changing environment settings.

### 4. Initialize or update the database schema

```bash
npm run db:setup --prefix backend
```

This applies the additive schema, including runtime connections and browser labs, without inserting sample records or deleting existing records. Run it again after pulling schema changes. The app uses the database in your local `DATABASE_URL`: pointing at the same database as deployment shares its accounts and records; a separate development database starts empty. When sharing saved runtime connections across backend instances, use the same stable `RUNTIME_CREDENTIALS_KEY` on those instances, or the same `SESSION_SECRET` if no dedicated key is set.

### 5. Start the application

```bash
npm run dev
```

Keep this terminal running. It starts both processes:

| Component | Local URL |
| --- | --- |
| Web application | http://localhost:5173 |
| Backend readiness | http://localhost:8787/api/health |
| Readiness through the frontend proxy | http://localhost:5173/api/health |

Open **http://localhost:5173/#/app**. Use `localhost` consistently with `FRONTEND_URL`. Vite exits if port 5173 is occupied, instead of silently moving to another port that the backend does not allow. Stop an older app instance before starting another. Press **Ctrl+C** to stop both development processes.

### 6. Verify the local workflows

1. Create a workspace, or sign in to an account in the configured database.
2. Open **Infrastructure → Browser test lab → Start lab** for Docker or Kubernetes. No Docker installation, collector or terminal command is needed for this workflow.
3. Choose a failure scenario, open its **Investigate** link, and inspect the marked test incident and timeline.
4. Select **Analyze evidence** to test your local OpenRouter configuration. Analysis must identify lab observations as simulated.
5. Return to the lab and select **Restore healthy**. The test incident resolves; its history remains available through **Test lab incidents** in the incident queue. Live dashboard metrics exclude lab records.
6. Open **Infrastructure → Live connections → Add connection** to connect an existing reachable HTTPS Docker/Portainer or Kubernetes API. The same public-address, verified-TLS and read-only request rules apply locally and on deployment. Local-only Docker sockets and private APIs are not accepted by these forms; use the browser lab or the [advanced collector](docs/CONTAINER-TRACKING.md#advanced-collector-setup).
7. Connect an HTTP service through **Services**, use **Check now**, and verify that notes, ownership, incident status and live updates persist.

Health checks for a running local app can also be inspected from a second terminal:

```bash
curl http://localhost:8787/api/health
curl http://localhost:5173/api/health
```

Both should return JSON with `"ok":true` and `"database":"connected"`. Local development uses the same application features as deployment; access to the database, AI provider and real monitoring endpoints depends on your configured credentials and network.

## Updating an existing local installation

Stop the running app with Ctrl+C, then run from its repository root:

```bash
git pull --ff-only origin main
npm run install:all
npm run setup:local
npm run db:setup --prefix backend
npm run dev
```

Keep existing `backend/.env` and `frontend/.env` files. Git does not update ignored environment files: if your database or provider changed, update those values locally too. Do not copy the example files over configured files. Confirm `VITE_API_URL=` is blank and `NODE_ENV=development` before starting locally.

## Preview the built frontend locally

To check compiled assets instead of the development server, stop `npm run dev` first:

```bash
npm run build
npm run start --prefix backend
```

Keep that backend running. In a second terminal at the repository root:

```bash
npm run preview --prefix frontend
```

Open http://localhost:5173. Preview uses the same local API proxy and port as development. Keep the local backend's `NODE_ENV=development` for these plain-HTTP localhost sessions. Vite preview is a local verification tool; production remains hosted on Vercel and Railway.

## Local troubleshooting

| Symptom | Fix |
| --- | --- |
| `tsx: command not found` or missing Vite/concurrently | Run `npm run install:all` from the repository root before setup/startup. |
| The local UI calls Railway, or sign-in has a cross-origin error | Set `VITE_API_URL=` blank in `frontend/.env`, use http://localhost:5173 and restart both servers. |
| `Origin is not allowed` | Match `FRONTEND_URL=http://localhost:5173` to the browser URL; do not switch to 127.0.0.1 or another port without updating it. |
| Port 5173 or 8787 is in use | Stop the earlier app instance or other process using that port, then restart. |
| Database not ready | Verify the full PostgreSQL URL and database availability, then run `npm run db:setup --prefix backend`. |
| Login succeeds but the session does not persist on localhost | Use `NODE_ENV=development`, a stable generated session secret, and the local API proxy. |
| Intelligence is disabled or the provider reports an error | Set a valid `OPENROUTER_API_KEY` and an available model in `backend/.env`, then restart the backend. |
| A new database has no services or incidents | Create a workspace and connect real services, or start an explicitly labelled browser lab. Setup does not seed operational records. |

## Real-time behavior

- Health endpoints are checked on their configured interval, with a 30-second minimum.
- Two consecutive failed checks mark a service down and create an incident.
- Recovery resolves health-monitor incidents and broadcasts the change.
- Critical keyed telemetry creates an incident immediately.
- Incident, service, analysis, and telemetry changes broadcast to all signed-in operators in the same organization.
- All application queries are scoped to the authenticated organization.

## API surface

- `POST /api/auth/register`, `POST /api/auth/login`, `GET /api/auth/me`
- `GET/POST /api/services`, `POST /api/services/:id/check`
- `GET/POST /api/incidents`, `PATCH /api/incidents/:id/status`
- `POST /api/incidents/:id/analyze`
- `POST /api/ingest/:serviceId` with `x-ingest-key`
- `GET /api/stream` for authenticated live events

## Stack

- Frontend: React, TypeScript, Tailwind CSS, Framer Motion, React Three Fiber, Recharts
- Backend: Express, TypeScript, Supabase PostgreSQL, signed HTTP-only sessions, SSE
- AI: OpenRouter with `openrouter/free` by default

## Operator controls and release verification

The cockpit includes incident search and filters, persisted responder notes and ownership, JSON incident export, service settings and monitoring pause, ingest-key rotation, recent signal history, and role-based workspace invitations and switching. Connection failures expose a retry action, and reconnecting live streams reload current records.

Health checks serialize per service; incident changes and their timelines commit together. Critical telemetry is deduplicated under concurrent requests. PostgreSQL notifications distribute committed updates across API replicas; Supabase uses a session-capable connection for the listener and a bounded connection pool for application traffic.

See [the operations runbook](docs/OPERATIONS.md) for deployment, database replacement, role permissions, verification, and the current capacity and feature limits. Run the integration suite only against an isolated `incident_test` database. GitHub Actions builds both applications, runs the suite with PostgreSQL, and lints the frontend.

## Docker and Kubernetes tracking

Open **Infrastructure**. Choose either workflow directly in the web app:

- **Live connections → Add connection**: connect Docker through Portainer (discover and select an environment), a secured Docker Engine API, or a Kubernetes API and namespace. Enter the HTTPS URL and read credentials, test access, then save. A service is created automatically unless you select an existing one. Inventory syncs every 30–300 seconds; Refresh, Pause/Resume, Reconnect and Remove are available in the same screen.
- **Browser test lab**: start a Docker or Kubernetes lab and choose a failure scenario. Inspect its test incident, timeline and optional AI analysis, then select **Restore healthy** to verify simulated recovery. Ending a session retains its history. No container or cluster is executed or modified by this lab. Test services/incidents stay out of live dashboard metrics and are available through the incident queue's **Test lab incidents** filter.

Real connections require an existing public, reachable HTTPS runtime API. The hosted app cannot access Docker Desktop's local socket or a private cluster directly. Custom CA and client TLS PEM uploads are supported; TLS verification stays enabled. Remote requests are GET-only, pinned to validated public DNS addresses, limited in size/time, and do not follow redirects. Credentials are encrypted at rest using a key derived from the backend session secret (or optional stable `RUNTIME_CREDENTIALS_KEY`); keep that key consistent across replicas and backups. Changing it requires reconnecting saved integrations.

The existing host/in-cluster collector remains an advanced option for private infrastructure. See [runtime connections, lab scenarios, detection rules and collector setup](docs/CONTAINER-TRACKING.md). No root environment file is required.
